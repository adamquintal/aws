## Instrument everything

The instrumentation guide's short answer is to **instrument everything**. The Zen of Prometheus says it as **"Instrument first, ask questions later"**: during development you can't know which questions you'll need to answer during an incident. A metric without labels is cheap, so spread them generously.

Define metrics in the same file where you use them. That makes it easy to go from an alert to a dashboard to the code.

## The three types of services

| Type | What it is | Key metrics |
|---|---|---|
| **Online-serving** | Someone is waiting for an immediate response (HTTP, database queries) | queries, **errors**, **latency**, requests in progress |
| **Offline processing** | No one waits; work is often batched and staged | per stage: items in, in progress, out, last processed time |
| **Batch jobs** | Don't run continuously, so they're hard to scrape | **last success timestamp**, stage durations, last completion, records processed |

Some details from the guide:

- **Online-serving:** monitor both the client and server side, because differences between them are valuable for debugging. Count queries **when they end**, so counts line up with errors and latency.
- **Offline processing:** a **heartbeat** is a dummy item carrying its insertion timestamp through every stage. It shows how long items take to propagate, not just whether one stage is stalled.
- **Batch jobs:** push the gauges to the Pushgateway. A long-running batch job can also be scraped. A job that runs more often than about every 15 minutes is probably better as a daemon.

## Subsystems worth covering

- **Libraries** should come instrumented with no configuration. For anything that touches the network, disk or IPC, track query count, errors and latency.
- **Logging:** for every logging line, increment a counter, and export totals of info, warning and error lines.
- **Failures:** increment a counter on every failure, and also track **total attempts**, so the failure ratio is easy to calculate.
- **Thread pools:** queued requests, threads in use and total threads, tasks processed and how long they took.
- **Caches:** total queries, hits and latency, plus the same for the system behind the cache.

## Habits that keep metrics useful

```promql
# Expose the raw counter in code…
http_requests_total
# …and let PromQL derive rates and ratios:
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))
```

- **Counters rule.** Expose raw counters and let `rate()` and `increase()` do the work. Precalculating rates on the target throws away information. Don't add metrics that are just aggregations; PromQL can do those.
- **Avoid missing metrics.** A series that only appears after the first error breaks dashboards and alerts. Export `0` for series you know may exist. Libraries do this automatically for unlabelled metrics, and for labelled ones you initialise the label values you expect.
- **Measure what users care about.** Users experience latency and availability, not CPU. Frameworks like **RED** (Rate, Errors, Duration), **USE** (Utilisation, Saturation, Errors) and **the Four Golden Signals** are good starting points. Keep internal metrics such as CPU for troubleshooting.

## Is it too expensive?

Usually not. A Java counter increment costs about **12–17 ns**. Only in code called **more than about 100,000 times a second** should you limit the metrics you update, avoid label lookups (or cache the child returned by `labels()`), and be careful with time measurements, which may need a syscall.
