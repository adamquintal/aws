## Rule files and groups

Rules live in YAML files that `prometheus.yml` loads with `rule_files`:

```yaml
rule_files:
  - "rules/*.yml"
```

Like the main config, rule files reload on `SIGHUP`, and changes only apply if **all** rule files are valid.

Inside a file, rules are organised into **groups**:

```yaml
groups:
  - name: example
    interval: 1m          # optional, defaults to global evaluation_interval
    rules:
      - record: code:prometheus_http_requests_total:sum
        expr: sum by (code) (prometheus_http_requests_total)
```

Rules in a group run **one after another, at the same evaluation time**, every `interval`.

## Recording rules

A recording rule evaluates `expr` every cycle and stores the result as new series named by `record`, which must be a valid metric name. That makes repeated queries much faster, which is especially useful for **dashboards** that re-run the same query on every refresh. Names follow `level:metric:operations` (see the naming topic).

## Alerting rules

From the official docs:

```yaml
groups:
- name: example
  rules:
  - alert: InstanceDown
    expr: up == 0
    for: 5m
    labels:
      severity: page
    annotations:
      summary: "Instance {{ $labels.instance }} down"
      description: "{{ $labels.instance }} of job {{ $labels.job }} has been down for more than 5 minutes."
```

| Field | Meaning |
|---|---|
| `alert` | The alert's name (CamelCase by convention) |
| `expr` | PromQL. **Every series it returns is an active alert** for that label set. |
| `for` | How long the condition must keep holding before the alert **fires**. Until then it's **pending**. Default 0s, which fires on the first evaluation. |
| `keep_firing_for` | Keep firing for this long after the condition clears, to avoid flapping. Default 0s. |
| `labels` | Extra labels such as `severity`. They overwrite conflicting ones and can be templated. |
| `annotations` | Longer, informational text: summary, description, runbook URL. Can be templated. |

### Templating

- `{{ $labels.instance }}` gives a label value of the alerting series.
- `{{ $value }}` gives the expression's value.
- `$externalLabels` gives the configured external labels.

## Inspecting alerts

- The **Alerts** tab in the Prometheus UI shows every pending and firing alert with its labels.
- Prometheus also writes synthetic series you can query:

```text
ALERTS{alertname="InstanceDown", alertstate="pending"|"firing", ...}   1
```

## Testing rules

```bash
promtool check rules /path/to/example.rules.yml   # syntax check, exit code 0 if valid
promtool test rules test.yml                      # unit tests with input series and expected alerts
```

## Getting alerts out

Prometheus's rules are good at working out **what's broken right now**, but Prometheus isn't a notification system. It sends alert states to **Alertmanager**, which handles grouping, rate limiting, silences and routing:

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ['alertmanager:9093']
```

Alertmanagers can be listed statically or found through service discovery.
