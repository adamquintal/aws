## Why counters need rate()

A raw counter is a running total since the process started, such as `http_requests_total = 18,442,019`. That number on its own tells you almost nothing. What you want is **how fast it's growing**. All the functions here take a **range vector** (some samples per series) and return an **instant vector** (one value per series).

## rate(): the workhorse

```promql
rate(http_requests_total{job="api-server"}[5m])
```

This returns the **per-second average rate of increase** over the last 5 minutes, for each series. Two things make it robust:

1. **Counter resets are handled.** When a process restarts, its counters drop to zero. `rate()` treats any decrease as a reset and adjusts, instead of seeing a giant negative change.
2. **Extrapolation.** It extrapolates to the edges of the window, which allows for missed scrapes and scrape times that don't line up with the window.

The docs recommend `rate()` for **alerting** and for graphing **slow-moving counters**.

## irate(): the last two points

```promql
irate(http_requests_total{job="api-server"}[5m])
```

`irate()` calculates the per-second rate from **only the last two samples** in the window. The `[5m]` here just says how far back to look for those two points. It reacts instantly, which suits graphs of **volatile, fast-moving counters**.

The docs warn against using it for alerts: brief changes can reset an alert's waiting period, and graphs made only of rare spikes are hard to read.

## increase(): total growth in the window

```promql
increase(http_requests_total{job="api-server"}[5m])
```

This is the **total number of requests in the last 5 minutes**. It's simply `rate()` multiplied by the number of seconds in the window, offered for readability. Because of extrapolation, it can return non-integer values even when the counter only goes up in whole steps. The docs suggest using `rate` in recording rules so increases are tracked consistently per second.

## Rate first, then aggregate

Soon you'll learn aggregation operators such as `sum()`. The rule to remember now: **take `rate()` (or `irate()`) first, then aggregate.** If you add up raw counters across several series first, a reset in one series is hidden inside the total, and `rate()` can no longer detect it.

## Functions for gauges

Gauges go up and down, so "counter reset" logic would be wrong for them. Use these instead:

| Function | What it gives you | Example |
|---|---|---|
| `delta(v[d])` | Difference between first and last value over the window, extrapolated | `delta(cpu_temp_celsius{host="zeus"}[2h])` is the change in CPU temperature over 2 hours |
| `idelta(v[d])` | Difference between the last two samples | |
| `deriv(v[d])` | Per-second derivative, using simple linear regression (needs at least 2 samples) | How fast a queue is growing |
| `predict_linear(v[d], t)` | Predicted value `t` seconds from now, using simple linear regression | Will the disk be full in 4 hours? |

An illustration of the classic "disk will fill up" pattern, using a Node Exporter gauge:

```promql
predict_linear(node_filesystem_avail_bytes[1h], 4 * 3600) < 0
```

This means: based on the last hour's trend, available space will be below zero 4 hours (14,400 seconds) from now.

## Counting events in a window

- `resets(v[d])` gives the number of counter resets in the window. Use it with counters.
- `changes(v[d])` gives the number of times the value changed in the window.
