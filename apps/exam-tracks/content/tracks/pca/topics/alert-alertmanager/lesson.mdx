## Two halves of alerting

1. **Prometheus** evaluates alerting rules and **sends alerts** to Alertmanager.
2. **Alertmanager** **manages** them: de-duplicating, grouping, routing, silencing and inhibiting, then sending **notifications** through **receivers** such as email, PagerDuty, Slack, OpsGenie or webhooks.

Alertmanager has its own YAML config, `alertmanager.yml`, loaded with `--config.file`.

## Grouping

During a big outage, hundreds of alerts can fire at once. **Grouping** combines alerts of a similar nature into **one notification** that still lists everything affected. The docs' example: a network partition makes half of many service instances lose their database. Group by `cluster` and `alertname`, and that's a single page.

Three timers shape a group's notifications:

| Setting | Default | Meaning |
|---|---|---|
| `group_wait` | **30s** | Wait before the **first** notification for a new group, so related alerts (and inhibiting ones) can arrive. An alert that resolves within it sends nothing. |
| `group_interval` | **5m** | Wait before sending an **update** when the group changes (new or resolved alerts) |
| `repeat_interval` | **4h** | Wait before **re-sending** a notification that hasn't changed |

## Routing

Routes form a **tree**. This is the docs' example:

```yaml
route:
  receiver: 'default-receiver'
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  group_by: [cluster, alertname]
  routes:
  - receiver: 'database-pager'
    group_wait: 10s
    matchers:
    - service=~"mysql|cassandra"
  - receiver: 'frontend-pager'
    group_by: [product, environment]
    matchers:
    - team="frontend"
```

- Every alert enters at the **root route**, which must match all alerts.
- It walks the child routes, matching on labels with **`matchers`**.
- With **`continue: false`** (the default), it **stops at the first matching child**. With `continue: true` it keeps checking later siblings.
- An alert that matches no child is handled by the current node, so here unmatched alerts go to `default-receiver`.
- Children **inherit** `receiver`, `group_by` and the timers from their parent unless they override them.

## Inhibition

**Inhibition** mutes some alerts *while other alerts are firing*:

```yaml
inhibit_rules:
  - source_matchers: [ alertname="ClusterDown" ]
    target_matchers: [ severity="warning" ]
    equal: [ cluster ]
```

While a `ClusterDown` alert fires, warning alerts **for the same cluster** (the `equal` labels must match) are muted. That saves hundreds of pages about symptoms of one root problem. Inhibition is defined in the config file.

## Silences

A **silence** mutes alerts that match its matchers **for a set period**, for example during planned maintenance. Silences are created in the **Alertmanager web UI** (or with `amtool`), not in the config file. Matching alerts send no notifications until the silence expires.

## High availability

Run several Alertmanagers as a **cluster**, using the `--cluster-*` flags. They gossip silences and notification state, and prefer sending a duplicate to missing an alert.

**Point Prometheus at every Alertmanager instance. Don't load-balance between them.** Each instance receives alerts directly and they de-duplicate between themselves.

## Checking the config

```bash
amtool check-config alertmanager.yml
```
