## Flags vs. the config file

Prometheus takes two kinds of configuration:

- **Command-line flags** set immutable system parameters: where to store data, how long to keep it, and so on. For example `--storage.tsdb.path` and `--storage.tsdb.retention.time`.
- **The configuration file**, YAML and loaded with `--config.file`, defines **what to scrape** (jobs and their instances) and **which rule files to load**.

## A real prometheus.yml

This is the starter config from the official getting-started guide:

```yaml
global:
  scrape_interval:     15s # By default, scrape targets every 15 seconds.
  external_labels:
    monitor: 'codelab-monitor'

scrape_configs:
  # The job name is added as a label `job=<job_name>` to any timeseries scraped from this config.
  - job_name: 'prometheus'
    # Override the global default and scrape targets from this job every 5 seconds.
    scrape_interval: 5s
    static_configs:
      - targets: ['localhost:9090']
```

Prometheus exposes its own metrics, so it can scrape itself.

### Global defaults (worth memorising)

| Setting | Built-in default | Meaning |
|---|---|---|
| `scrape_interval` | **1m** | How often to scrape targets |
| `scrape_timeout` | **10s** | How long a scrape may take. Can't be greater than the interval. |
| `evaluation_interval` | **1m** | How often rules are evaluated |

The example above sets 15s, which is common, but the default when unset is 1 minute. Settings in `global` act as defaults that each `scrape_config` can override.

`external_labels` are added to series and alerts only when Prometheus talks to *external* systems: federation, remote storage and Alertmanager.

## scrape_config: one job

Each entry under `scrape_configs` usually defines one job:

```yaml
scrape_configs:
  - job_name: 'node'
    scrape_interval: 5s
    static_configs:
      - targets: ['localhost:8080', 'localhost:8081']
        labels:
          group: 'production'
      - targets: ['localhost:8082']
        labels:
          group: 'canary'
```

(From the getting-started guide.) Targets can be listed statically with `static_configs`, or found dynamically through service discovery, which is covered in a later topic. Useful per-job settings and their defaults:

- `metrics_path`: `/metrics`
- `scheme`: `http`
- `honor_labels`: `false`. If scraped data already has a label Prometheus wants to attach, such as `job` or `instance`, the scraped one is renamed to `exported_job` or `exported_instance`. Set it to `true` to keep the scraped values instead. That's useful for federation and for scraping the Pushgateway.
- `honor_timestamps`: `true`, meaning timestamps exposed by the target are used.

## Reloading

Prometheus can reload its config without restarting:

- send the process a `SIGHUP`, or
- `POST` to `/-/reload`, if the `--web.enable-lifecycle` flag is enabled.

If the new file isn't valid, the change isn't applied. Rule files are reloaded at the same time.

## Relabeling

**Target relabeling** (`relabel_configs`) rewrites a target's labels **before it is scraped**. Steps run in order. Each one reads `source_labels`, matches a `regex` against them, and performs an `action`:

| Action | Effect |
|---|---|
| `replace` (default) | Write `replacement` (with capture groups) into `target_label` |
| `keep` | Drop targets whose source labels *don't* match |
| `drop` | Drop targets whose source labels *do* match |
| `labelmap` | Copy labels whose *names* match the regex to new names |
| `labeldrop` / `labelkeep` | Remove labels whose names match / don't match |
| `hashmod` | Set a label to a hash modulus, used for sharding |

Details that come up often:

- Regexes are **RE2** and **anchored on both ends**, so `regex: foo` only matches exactly `foo`. Use `.*foo.*` to match anywhere.
- Special labels such as `__address__`, `__scheme__` and `__metrics_path__` control how the target is scraped. Service discovery adds `__meta_*` labels.
- After relabeling, **labels starting with `__` are removed**, and `instance` is set from `__address__` if you didn't set it yourself.

**Metric relabeling** (`metric_relabel_configs`) uses the same format but is applied **to scraped samples, as the last step before ingestion**. A typical use is dropping series that are too expensive to store. It doesn't affect automatically generated series such as `up`.

```yaml
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'expensive_metric_.*'
    action: drop
```
