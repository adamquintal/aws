## Pull is the default

Prometheus **pulls** metrics. On a schedule, the server makes an HTTP request to each target and reads the current values. Targets don't need to know where Prometheus is, or even that it exists.

The FAQ lists the advantages of pulling over HTTP:

- **You can start extra monitoring instances freely**, for example on your laptop while developing a change, without reconfiguring anything.
- **You can tell more easily and reliably that a target is down.** If the scrape fails, Prometheus knows.
- **You can inspect a target by hand**: open its `/metrics` page in a browser.

The FAQ is also refreshingly modest. It says pulling is only *slightly* better than pushing, and that it shouldn't be a major point when choosing a monitoring system.

## The `up` metric: health checks for free

Every scrape produces a sample in a synthetic series:

```text
up{job="<job-name>", instance="<instance-id>"}   1 if the scrape succeeded, 0 if it failed
```

Because Prometheus initiates every scrape, it always knows whether a target answered. `up == 0` is one of the most common alert conditions you'll meet.

## Pushing: the Pushgateway

Some things can't be scraped. A **batch job** might run for 20 seconds and exit long before Prometheus would come by. For these, Prometheus offers the **Pushgateway**, an intermediary service. The job pushes its metrics there, and Prometheus scrapes the Pushgateway like any other target.

The best-practices page is blunt: the Pushgateway is recommended **only in certain limited cases**, because using it as a general push mechanism has real costs:

1. **Single point of failure and bottleneck.** Many instances funnel through one gateway.
2. **You lose `up`.** Prometheus scrapes the gateway, not your job, so it can't tell whether your job is healthy.
3. **It never forgets.** Pushed series stay exposed forever until someone deletes them through the Pushgateway's API, even after the instance that pushed them is renamed or removed. With pull, a target's metrics vanish along with the target.

**The usual valid use case is capturing the outcome of a service-level batch job.** That's a job not tied to a specific machine or instance, such as "delete inactive users across the whole service". Its metrics shouldn't carry a machine or instance label.

## Alternatives

- **A firewall or NAT blocks scraping?** Run Prometheus on the same network as the targets, which the docs generally recommend anyway, or use **PushProx** to traverse the barrier.
- **Batch job tied to one machine** (for example a cron job doing security updates)? Write its results to a file for the **Node Exporter textfile collector** instead of using the Pushgateway.

The text exposition format is simple enough that even a shell script can push metrics to the Pushgateway without a client library.
