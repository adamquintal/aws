## Two time functions

| Function | Returns |
|---|---|
| `time()` | The **evaluation time** as seconds since 1970-01-01 UTC. In a range query that's each step's time, not the wall clock. |
| `timestamp(v)` | The **timestamp of each sample** in `v`, in seconds since the epoch |

```promql
time() - timestamp(up)    # how old is each target's latest up sample?
```

## Timestamps, not "time since"

The instrumentation guide gives a clear rule. If you want to know **how long ago** something happened, **export the Unix timestamp at which it happened**, not the time elapsed since.

```promql
time() - my_timestamp_metric
```

Why? A "seconds since" gauge needs code that keeps updating it. If that code gets stuck, the value freezes and looks healthy. A timestamp never needs updating. PromQL works out the elapsed time at query time, using `time()`.

### Naming

By convention timestamp metrics end in `_timestamp_seconds`, in base units with the unit suffix:

```text
data_pipeline_last_record_processed_timestamp_seconds
```

### Real examples

Client libraries expose the process start time as a gauge:

```text
# HELP process_start_time_seconds Start time of the process since unix epoch in seconds.
# TYPE process_start_time_seconds gauge
process_start_time_seconds 1.54115492874e+09
```

(From the multi-target exporter guide.) So the uptime of every process is:

```promql
time() - process_start_time_seconds
```

For **batch jobs**, the docs name the key metric as **the last time the job succeeded**, exported as a timestamp gauge and usually pushed to the Pushgateway. "Hasn't succeeded for over a day" then becomes:

```promql
time() - my_batch_job_last_success_timestamp_seconds > 86400
```

## Turning timestamps into calendar parts

These functions read sample values **as Unix timestamps** and return calendar parts in **UTC**. With no argument, they use `vector(time())`:

| Function | Range |
|---|---|
| `day_of_week()` | 0 to 6 (0 = Sunday) |
| `day_of_month()` | 1 to 31 |
| `day_of_year()` | 1 to 365/366 |
| `hour()` | 0 to 23 |
| `minute()`, `month()`, `year()`, `days_in_month()` | as named |

```promql
day_of_week()                           # today's weekday, in UTC
hour(process_start_time_seconds)        # the UTC hour each process started
```

## Exporters and timestamps

The exporter-writing guide says exporters generally **shouldn't set timestamps** on the samples they expose. Let Prometheus use the scrape time. (If you think you need custom timestamps, the guide suggests you probably want the Pushgateway.) Remember the unit difference: optional timestamps in the exposition format are **milliseconds**, while PromQL's time functions work in **seconds**.
