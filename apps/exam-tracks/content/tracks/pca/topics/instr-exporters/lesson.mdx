## When you need an exporter

Client libraries work when you own the code. When you don't (the Linux kernel, HAProxy, MySQL, a network switch), you run an **exporter**. It fetches the system's stats in whatever form they come and exposes them as Prometheus metrics on `/metrics`.

Some exporters are **official** (maintained in the Prometheus GitHub organisation), and many more are community-maintained. Familiar ones:

| Exporter | What it covers |
|---|---|
| **Node Exporter** | Linux and Unix host metrics such as CPU, memory, disk and network. Port **9100**, metrics prefixed `node_`. |
| **Blackbox exporter** | Probes endpoints over HTTP, DNS, TCP or ICMP from the outside |
| **SNMP exporter** | Network devices speaking SNMP |
| **JMX exporter** | JVM applications, for example Kafka and Cassandra |
| **HAProxy, MySQL exporters** | Their respective systems |

Scraping the Node Exporter (from the official guide):

```yaml
scrape_configs:
- job_name: node
  static_configs:
  - targets: ['localhost:9100']
```

## How good exporters behave

### One per instance, beside it

Each exporter should monitor **exactly one application instance, running next to it**. That's one `haproxy_exporter` for every HAProxy. It mirrors what direct instrumentation would give you, and it means **service discovery stays in Prometheus**.

### The multi-target exception

Some exporters can't sensibly run beside their target:

- **SNMP and IPMI**: the devices are black boxes you can't run code on.
- **Blackbox**: you specifically want to measure from *outside*, for example a website's reachability.

These use the **multi-target exporter pattern**. One exporter queries many targets over the network. Prometheus still discovers the targets, then passes each one (and a module) as **URL parameters** in the scrape request, usually set up with relabeling. The exporter starts its probe when the request arrives.

### Synchronous scrapes, no timestamps

Pull metrics from the application **only when Prometheus scrapes**, with no background timers. So **don't set timestamps** on samples; Prometheus assigns them. (If you think you need timestamps, the guide suggests you probably want the Pushgateway.) Mind the **10-second default scrape timeout**. Anything very slow (over a minute) may be cached, noted in the HELP string.

### Leave labels to Prometheus

If you want the same label on every metric (`region`, `cluster`), **stop**. Those are **target labels**, and they belong in Prometheus's scrape config and service discovery. Different teams may label the same application differently.

### Types and help

- Map source metrics to Prometheus types, usually counters and gauges. **If unsure, use untyped.**
- A "counter" from another system that can go **down** isn't a counter. Use untyped rather than a misleading gauge.
- Put the original metric's name and any transformation rule in the HELP string.

### Failed scrapes

Two patterns when the application doesn't respond:

1. Return an HTTP **5xx**. Prometheus's own `up` then shows 0, but you can't tell "exporter down" from "app down".
2. Expose a **`myexporter_up`** gauge (such as `haproxy_up`) of 0 or 1. This is better when some metrics, like process stats, are still useful.

### Don't duplicate

- Drop machine metrics such as CPU and memory that the application also exposes, because the Node Exporter covers them.
- Don't add scrape counters or scrape-duration histograms. Prometheus already records `up`, `scrape_duration_seconds` and the rest. A gauge such as `jmx_scrape_duration_seconds` is fine.

### Ports

Each exporter has its own default port, tracked on the Prometheus wiki's **default port allocations** page, so many can run on one machine.
