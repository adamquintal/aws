## Two ways to describe a distribution

For request durations or response sizes you care about the **distribution**, not just one number. Prometheus offers two approaches:

| | Summary | Histogram |
|---|---|---|
| Who calculates percentiles? | The application, over a sliding window | The Prometheus server, with `histogram_quantile()` |
| Can you pick a different percentile or window later? | No, they're fixed at instrumentation time | Yes, in the query |
| Can you aggregate across instances? | **No** | **Yes** |
| Cost per observation | Relatively expensive | Cheap (just increments counters) |
| Accuracy | Generally very accurate | Limited by bucket width (classic) or resolution (native) |

## Classic histogram series

```text
http_request_duration_seconds_bucket{le="0.1"}  33444
http_request_duration_seconds_bucket{le="0.2"} 100392
http_request_duration_seconds_bucket{le="0.5"} 129389
http_request_duration_seconds_bucket{le="+Inf"} 144320
http_request_duration_seconds_sum   53423
http_request_duration_seconds_count 144320
```

`le` means "less than or equal": each bucket counts **all** observations up to its bound, so the buckets are cumulative.

## Percentiles with histogram_quantile()

The 90th percentile of request duration over the last 10 minutes (from the docs):

```promql
histogram_quantile(0.9, rate(http_request_duration_seconds_bucket[10m]))
```

- `rate()` sets the **time window**. Buckets are counters, so you always rate them first.
- The result is calculated **per label combination**, for example per instance.

To aggregate, **sum the bucket rates, keeping `le`**:

```promql
# 90th percentile per job
histogram_quantile(0.9, sum by (job, le) (rate(http_request_duration_seconds_bucket[10m])))

# 90th percentile across everything
histogram_quantile(0.9, sum by (le) (rate(http_request_duration_seconds_bucket[10m])))
```

`histogram_quantile()` uses `le` to know which bucket is which. Drop it and the calculation can't work.

### How it estimates

The answer is an **estimate**. For classic histograms, it assumes observations are spread evenly within the bucket the quantile lands in (**linear interpolation**), so the error is bounded by that bucket's width. Special cases:

- If the quantile falls in the top (`+Inf`) bucket, it returns the **upper bound of the second-highest bucket**.
- Fewer than two buckets, or a highest bucket that isn't `+Inf`, gives `NaN`.

## Averages and rates from _sum and _count

```promql
# average request duration over 5 minutes
rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])

# requests per second (the _count series behaves exactly like a request counter)
rate(http_request_duration_seconds_count[5m])

# average per job: aggregate after the rate, before dividing
sum by (job) (rate(http_request_duration_seconds_sum[5m]))
/
sum by (job) (rate(http_request_duration_seconds_count[5m]))
```

## "What fraction were fast enough?"

Suppose your target is 95% of requests within 300 ms. With classic histograms, divide the rate of the 0.3 bucket by the rate of the count:

```promql
sum by (job) (rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
/
sum by (job) (rate(http_request_duration_seconds_count[5m]))
```

This **requires a bucket boundary at exactly 0.3**. With no such bucket you get no result, not an estimate. (Note the base unit: 300 ms is written `0.3` seconds.) The same bucket arithmetic powers **Apdex** scores.

## Don't average summary quantiles

```promql
avg(http_request_duration_seconds{quantile="0.95"})                                   # BAD
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))  # GOOD
```

Averaging pre-calculated percentiles from several instances gives a statistically meaningless number. That's the main reason to choose histograms.

## Rules of thumb from the docs

1. If you can, use **native histograms** at a resolution that fits your accuracy needs.
2. If not, and you need **aggregation**, use **classic histograms** with buckets chosen around the values you care about.
3. Consider **summaries** only when aggregation isn't needed.
