## The components

The Prometheus ecosystem is several programs, and most of them are optional:

| Component | What it does |
|---|---|
| **Prometheus server** | Scrapes metrics, stores them as time series, evaluates rules. The heart of the system. |
| **Client libraries** | Libraries (Go, Java, Python, Ruby, Rust and others) you use inside your own code to define metrics and expose them over HTTP. |
| **Exporters** | Separate programs that run next to something you can't change, such as a database or a Linux host, and translate its stats into Prometheus format. |
| **Pushgateway** | Holds metrics pushed by short-lived batch jobs, so Prometheus can scrape them after the job has finished. |
| **Alertmanager** | Receives alerts from Prometheus, groups and de-duplicates them, applies silences, and sends notifications to email, Slack, PagerDuty and so on. |
| **Grafana / API clients** | Visualise data by sending PromQL queries to the server's HTTP API. |

Most components are written in Go and ship as single static binaries.

## How data flows

1. Your application (or an exporter next to it) serves its current metric values over HTTP, usually at `/metrics`. Each thing Prometheus collects from is a **target**. A group of targets doing the same job (say, five replicas of the same API) is a **job**.
2. The server **scrapes** each target on a schedule, meaning it pulls the current values over HTTP.
3. Every scraped value is stored as a sample in the server's own **time series database (TSDB)** on local disk.
4. The server periodically evaluates **rules**:
   - **Recording rules** precompute frequently used or expensive expressions and save the results as new time series.
   - **Alerting rules** check a condition. While the condition holds, an **alert** fires and is sent to Alertmanager.
5. **Alertmanager** turns alerts into **notifications** and decides who receives them.
6. You explore the data with **PromQL**, the Prometheus query language, in the built-in UI, in Grafana, or over the API.

## Storage, briefly

The local TSDB groups incoming samples into **two-hour blocks** on disk. The block currently being written lives in memory and is protected by a **write-ahead log (WAL)**, which is replayed if the server crashes and restarts. Older blocks are compacted into larger ones in the background.

Local storage belongs to a single node. It isn't clustered or replicated. For long-term or durable storage, Prometheus can send samples to other systems with **remote write** and read them back with **remote read**.

## Designed to keep working in an outage

The overview stresses that each Prometheus server is standalone: it doesn't depend on network storage or other remote services. That's deliberate. You want your monitoring to keep working when other parts of your infrastructure are broken, because that's exactly when you need it.
