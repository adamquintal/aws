## Why tracing

In a microservice or serverless system, one click can touch a gateway, several services and a database. When it's slow, metrics show *that* latency rose and logs show scattered messages, but neither shows the **path of that one request**. **Distributed tracing** does. It's especially valuable for problems that are hard to reproduce locally.

## Traces and spans

- A **trace** records the path of a **single request** as it travels through multiple services.
- A trace is made of **spans**. Each span is **a single unit of work**: an HTTP handler, a database query, a function call.
- The first span is the **root span**, covering the request start to finish. **Child spans** beneath it show the steps.

The OpenTelemetry primer's example: a page load passes through an API gateway, a backend service and a database. Each step is a span, and together they form one trace.

Tracing backends usually draw this as a **waterfall**, with nested bars showing which step took the time:

```text
GET /checkout ████████████████████████████████  4.0s   (root span)
  api-gateway  ██                                 0.1s
  cart-service    ████████████████████████████    3.8s
    db.query        ███████████████████████       3.4s   ← there it is
```

## What's inside a span

From the OpenTelemetry docs, a span includes:

| Part | Meaning |
|---|---|
| Name | What the operation is, such as `/v1/sys/health` |
| Parent span ID | Which span it's nested under (empty for the root) |
| Start and end timestamps | How long it took |
| **Span context** | **Trace ID** (shared by every span in the trace), span ID, trace flags, trace state |
| **Attributes** | Key-value metadata, such as `http.route`, `http.response.status_code` |
| **Span events** | Timestamped, structured messages within the span |
| **Links** | References to spans in other traces |
| **Status** | `Unset` (default, completed without error), `Error`, or `Ok` (explicitly marked successful) |

**Span kind** hints how spans connect: **Client** (outgoing call), **Server** (incoming call), **Internal** (inside one process, the default), **Producer** (creates a queued job) and **Consumer** (processes it later).

## Context propagation

How do spans from different services end up in the same trace? **Context propagation** passes the span context, carrying the trace ID, along with each request, for example in HTTP headers. Every service creates its spans under the same trace ID and the right parent, so the backend can assemble the whole trace.

## Where Prometheus fits

Prometheus is a metrics system and **doesn't store traces**. The bridge is **exemplars**: in the OpenMetrics format, a metric sample, such as a slow histogram bucket observation, can carry an exemplar with a **trace ID**. From a latency spike on a graph you can jump to an example trace in your tracing backend. (Exemplar storage is an experimental Prometheus feature that has to be enabled.)

The three signals work together. **Metrics** tell you something is wrong, **traces** show where, and **logs**, ideally carrying trace and span IDs, show the details.
