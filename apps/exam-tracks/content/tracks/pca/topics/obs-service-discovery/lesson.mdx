## Why discovery?

In a cloud or Kubernetes environment, instances appear, move and disappear constantly. Hard-coding IP addresses in `static_configs` breaks quickly. **Service discovery (SD)** lets Prometheus ask an authoritative system "what should I be scraping right now?" and keep the target list up to date on its own.

Every `scrape_config` can use static targets, one or more SD mechanisms, or both.

## Some common mechanisms

| Mechanism | Config block | How it finds targets |
|---|---|---|
| Kubernetes | `kubernetes_sd_configs` | Watches the Kubernetes REST API and stays in sync with cluster state |
| Consul | `consul_sd_configs` | Asks Consul's service catalog |
| AWS EC2 | `ec2_sd_configs` | Lists EC2 instances |
| DNS | `dns_sd_configs` | Periodically queries A, AAAA, MX, NS or SRV records |
| File | `file_sd_configs` | Reads target lists from local YAML or JSON files |
| HTTP | `http_sd_configs` | Fetches a JSON target list from an HTTP endpoint |

There are many more (Azure, GCE, Docker, Nomad, OpenStack and so on).

### Kubernetes roles

Kubernetes SD has a `role` that decides what becomes a target:

- `node`: one target per cluster node
- `service`: one target per service port, generally useful for blackbox probing
- `pod`: one target per declared container port
- `endpoints` / `endpointslice`: targets from a service's endpoints
- `ingress`: one target per ingress path, also mainly for blackbox probing

### File-based SD: the universal adapter

File SD reads lists of static configs from files:

```yaml
- targets: ['10.0.0.5:9100', '10.0.0.6:9100']
  labels:
    env: 'prod'
```

Changes are picked up through **disk watches and applied immediately**, with no restart or reload needed (files are also re-read periodically as a fallback). Because anything can write a file, file SD is the docs' suggested way to plug in a discovery system Prometheus doesn't support natively.

**HTTP SD** is the network equivalent. Prometheus fetches JSON from a URL every `refresh_interval`, which defaults to 60s.

## Metadata labels and relabeling

Each discovered target comes with `__meta_*` labels describing it, for example:

```text
__meta_kubernetes_namespace="shop"
__meta_kubernetes_pod_name="cart-7d9f…"
__meta_filepath="/etc/prometheus/targets/web.yml"
```

These exist **only during relabeling**. Because they start with `__`, they're dropped once relabeling ends. To keep any of them, copy them into an ordinary label:

```yaml
relabel_configs:
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace
```

(With no `action`, this uses the default `replace`, and the default regex `(.*)` copies the whole value.) You can also use `keep` and `drop` on metadata to choose which discovered targets to scrape at all.

## Discovery lives in Prometheus

The exporter-writing guide makes a design point: **service discovery is done in Prometheus, not in exporters**. Exporters should stay simple. Prometheus finds the targets and decides what to scrape.
