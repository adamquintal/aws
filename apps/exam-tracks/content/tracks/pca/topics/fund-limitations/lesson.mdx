## Designed for reliability, not completeness

Prometheus's design goal is to be **the system you go to during an outage**. Each server is standalone and depends on nothing else. That focus brings some deliberate trade-offs.

### 1. Not for 100% accuracy

The overview says it directly: if you need 100% accuracy, **such as per-request billing**, Prometheus isn't a good choice. The data won't be detailed and complete enough. Use another system for billing and keep Prometheus for the rest of your monitoring.

### 2. Not an event or log store

Prometheus collects **metrics**: numbers sampled at intervals. It doesn't record individual events. The FAQ answers "How do I feed logs into Prometheus?" with "**Don't!**" and points to log systems such as Grafana Loki or OpenSearch. (Logs and events get their own topic later.)

### 3. Local storage is single-node

The storage docs note that local storage is **not clustered or replicated**, so it isn't arbitrarily scalable or durable against disk or node failure. Treat it like any other single-node database:

- Default retention is **15 days** (`--storage.tsdb.retention.time`), and you can also cap it by size (`--storage.tsdb.retention.size`).
- Prometheus stores an average of **1–2 bytes per sample**, so needed disk ≈ retention seconds × samples per second × bytes per sample.
- Use **snapshots** for backups. **NFS (including AWS EFS) isn't supported** for local storage.
- For long-term or durable storage, use **remote write / remote read** integrations.

### 4. Cardinality is the real scaling limit

The FAQ says a single Prometheus server can run reliably with **tens of millions of active series**, and calls "Prometheus doesn't scale" mostly a marketing claim. What breaks servers in practice is **cardinality explosions**: labels with unbounded values such as user IDs. Beyond one server, options include federation and long-term storage systems.

### 5. High availability is "run two"

There's no built-in clustering of the server. For HA, **run identical Prometheus servers on two or more machines**, all scraping the same targets. Then:

- systems such as **Thanos**, or many remote-write backends, can deduplicate the data;
- **Alertmanager** deduplicates the identical alerts both servers send, and can itself be clustered for HA.

### 6. Numbers and time

- Every sample value is a **64-bit float**. Integers are exact up to **2⁵³**. The FAQ notes that a counter incremented a million times a second would take over 285 years to hit precision issues.
- Internally everything is **Unix time**, and all components display **UTC**, to avoid timezone and daylight-saving confusion.

### 7. Pull has prerequisites

Prometheus must be able to **reach** its targets over the network, and very short-lived jobs need the **Pushgateway**, which has trade-offs of its own. Firewalls and NAT are usually solved by running Prometheus inside the network.

## The honest summary

The comparison page puts it well. Prometheus is better if you're **primarily doing metrics** and want powerful querying, alerting and high availability for graphing and alerting. A clustered or event-logging system is the better fit for **event logging** or for clustered, long-term historical storage on its own.
