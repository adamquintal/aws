## What identifies a time series

Prometheus stores everything as time series: streams of timestamped values that share the same metric name and the same set of **labels**. A label is a key-value pair such as `method="POST"`.

The usual notation is the metric name followed by labels in braces:

```text
api_http_requests_total{method="POST", handler="/messages"}
```

These are **three different time series**:

```text
api_http_requests_total{method="POST", handler="/messages"}
api_http_requests_total{method="GET",  handler="/messages"}
api_http_requests_total{method="POST", handler="/users"}
```

Same metric name, but the label values differ, so each is its own stream of data. The docs are explicit: changing any label value, or adding or removing a label, creates a new time series. This is the **dimensional data model**. Labels are dimensions you can later filter and aggregate by with PromQL.

## Samples

The actual data points are **samples**. Each sample is:

- a value, which is a 64-bit float (or a native histogram), and
- a timestamp with millisecond precision.

## The metric name is a label too

Internally, the metric name is stored as a special label called `__name__`. So these two notations point at the same series:

```text
http_requests_total{job="api"}
{__name__="http_requests_total", job="api"}
```

## Naming rules worth remembering

- Recommended metric name characters are letters, digits, underscores and colons, and the name must not start with a digit.
- **Colons are reserved for recording rules**, so exporters and instrumented code shouldn't use them.
- Label names beginning with **two underscores (`__`)** are reserved for Prometheus internals.
- A label with an **empty value** is treated as if the label weren't there.

## Labels Prometheus adds for you: job and instance

When Prometheus scrapes a target, it attaches two labels to everything it collects:

- `job`: the configured job name the target belongs to.
- `instance`: the `host:port` of the target that was scraped. An **instance** is one scrapeable endpoint, usually one process.

So an API job with four replicas produces four instances, and every series scraped from them is labelled with both `job` and `instance`.

## Labels have a cost: cardinality

Every unique combination of labels is another series, and each one uses RAM, CPU, disk and network. The number of distinct series a metric has is its **cardinality**.

The instrumentation guide offers rough guidance:

- Keep most metrics' cardinality **below 10**, and most metrics should have **no labels at all**.
- If a metric has, or could grow to, cardinality **over 100**, look for another approach.
- Never use unbounded values like **user IDs or email addresses** as label values.

A good label has a small, known set of values: `method`, `code`, `stage`, `operation`. If you're unsure, start with no labels and add them when a real need appears.
