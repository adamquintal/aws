## Anatomy of a good metric name

```text
http_request_duration_seconds        a histogram of request durations
process_cpu_seconds_total            a counter with a unit
http_requests_total                  a counter without a unit
node_memory_usage_bytes              a gauge in bytes
foobar_build_info                    a metadata pseudo-metric
data_pipeline_last_record_processed_timestamp_seconds
```

(All examples from the naming guide.) Read left to right, a name is:

1. **Application prefix**, one word: `prometheus_`, `process_`, `http_`. Client libraries sometimes call this the *namespace*.
2. **What's measured**: `request_duration`, `cpu`.
3. **Unit, plural**: `seconds`, `bytes`.
4. **`_total`** if it's an accumulating count. It goes **after** the unit: `process_cpu_seconds_total`.

### Base units

Prometheus has no units built in, so everyone sticks to **base units**:

| Family | Base unit | Notes |
|---|---|---|
| Time | seconds | not milliseconds |
| Data | bytes | even where bits are common |
| Length | meters | |
| Temperature | celsius | kelvin only where absolute temperature matters |
| Percent | ratio (0–1) | suffix `_ratio`, typical name `A_per_B` |
| Mass | grams | not kilograms |
| Energy / power | joules | export a joules counter; `rate()` gives watts |

### One meaning per metric

A metric should measure **the same logical thing across all its labels**. The test: **`sum()` or `avg()` across every dimension should make sense**. Capacities of several queues in one metric is fine. Capacity *and* current length in one metric is not, so split it.

## Labels, not names

Use labels to tell apart characteristics of the thing being measured:

```text
api_http_requests_total{operation="create|update|delete"}
api_request_duration_seconds{stage="extract|transform|load"}
```

- **Don't put label names in metric names.** Avoid `http_requests_get_total` and use a `method` label. Otherwise the name stops making sense once that label is aggregated away.
- **Never generate names procedurally.** Dynamic names are a sign you should be using labels.
- **Keep label values bounded.** Every combination is a new series.

## Names for recording rules

Recording rules follow **`level:metric:operations`**, which is why colons are reserved for them:

```yaml
- record: instance_path:requests:rate5m
  expr: rate(requests_total{job="myjob"}[5m])

- record: path:requests:rate5m
  expr: sum without (instance)(instance_path:requests:rate5m{job="myjob"})
```

(From the recording rules guide.)

- **level**: the labels left in the output (`instance_path`, `path`, `job`).
- **metric**: unchanged, except `_total` is stripped after `rate()`.
- **operations**: newest first (`rate5m`, `ratio_rate5m`, `mean5m`). Divisions name both metrics with `_per_` and use the operation `ratio`, as in `job:request_failures_per_requests:ratio_rate5m`.
